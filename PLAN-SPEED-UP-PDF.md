# План ускорения PDF-читалки

## Назначение документа

Этот файл — самодостаточная передача задачи следующему агенту. Цель работы: устранить многосекундную задержку появления PDF-страницы после быстрого пролистывания тяжёлых книг, сохранив существующий интерфейс и возможности Book Hub.

Исходная миграция с pdf.js на PDFium через `@embedpdf/engines` находится в коммите `d286bcf` (`embed`). На момент диагностики рабочая ветка — `embed`, версии `@embedpdf/engines`, `@embedpdf/models` и `@embedpdf/pdfium` — `2.15.0`.

## Ожидаемый результат

После исправления PDF-читалка должна:

- показывать первые пиксели целевой страницы без ожидания рендера давно ушедших страниц;
- не создавать canvas размером в десятки тысяч пикселей по высоте для всей страницы;
- удерживать ограниченный и проверяемый объём растровой памяти;
- сохранять автоширину, увеличение ширины, непрерывную прокрутку, прогресс чтения, историю навигации, оглавление, поиск, выделение текста, формы, аннотации и фильтры страницы;
- продолжать использовать общий UX книг с фиксированной вёрсткой, описанный в `docs/adr/0005-shared-fixed-layout-book-reader.md`;
- честно документировать фактическую загрузку PDF целиком, пока выбранный движок не поддерживает HTTP Range.

## Подтверждённая диагностика

Тест проводился 7 августа 2026 года на локальном dev-сервере `http://localhost:5173/` с книгой «хакер 322»:

- идентификатор книги: `ef8f0352-2e3e-4c82-af52-c355031638ef`;
- размер файла: `190 344 421` байт;
- количество страниц: 44;
- многие страницы имеют экстремальное отношение высоты к ширине; например, страница 8 имеет размер PDF примерно `768.96 × 10481`;
- backend отдаёт `Accept-Ranges: bytes`, но клиент делает один `GET 200` на весь файл, без запросов `206`;
- загрузка файла на localhost занимала примерно 2,7 секунды, метаданные страниц становились доступны примерно через 4 секунды.

### Замеры рендера

| Сценарий                                |       Book Hub |                    `app.embedpdf.com` |
| --------------------------------------- | -------------: | ------------------------------------: |
| Прямой переход на страницу 40           |    1,21–1,25 с |                           1,46–1,59 с |
| Быстрые переходы 12 → 20 → 28 → 36 → 40 |      4,2–5,6 с |                          около 1,46 с |
| CSS-ширина страницы по умолчанию        |  около 1400 px | около 154 px, автоматический zoom 20% |
| Внутренний растр страницы 40            | `1398 × 23313` |                          `384 × 6411` |

Прямой переход показывает, что сам PDFium не является главным источником регрессии. Задержка возникает при накоплении работы после быстрого изменения видимой области.

Для страницы 40 canvas `1398 × 23313` содержит около 32,6 млн пикселей и требует примерно 124 МиБ только под один RGBA-буфер. После быстрого перехода через несколько страниц Book Hub успевал создать десять больших canvas для страниц 11, 12, 19, 20, 27, 28, 35, 36, 39 и 40. Суммарный размер только их RGBA-поверхностей — около 1 ГиБ, без учёта временных `ImageData`, памяти WASM, текстового слоя, фильтрованных canvas и ресурсов браузера/GPU.

Зависимость времени от ширины подтверждена отдельно:

| Ширина viewport | Canvas страницы 40 | Время прямого рендера |
| --------------: | -----------------: | --------------------: |
|         1440 px |     `1398 × 23313` |               1216 мс |
|          400 px |       `358 × 5970` |                396 мс |
|          280 px |       `278 × 4636` |                355 мс |

### Первопричины

1. **Рендерится вся страница целиком.** `PdfReader.tsx` вычисляет scale только по ширине, вызывает `renderPageRaw()` для полной страницы, получает полный RGBA-буфер и копирует его в canvas через `new ImageData(...)` и `putImageData(...)`. Для очень высоких страниц стоимость растёт пропорционально площади.

2. **Задачи проходят через последовательную очередь PDFium.** В установленном `@embedpdf/engines` внутренний `WorkerTaskQueue` имеет `concurrency: 1`. `renderPageRaw` получает высокий приоритет, `getPageTextRects` — средний. Book Hub запускает рендер изображения и текстового слоя для каждой страницы из `visiblePages`.

3. **Отмена уже начавшейся операции не освобождает worker.** Abort возвращённой orchestrator-задачи удаляет ещё не начавшуюся запись из очереди, но не вызывает abort реальной PDFium-задачи, если она уже была извлечена из очереди. Результат может быть проигнорирован приложением, однако дорогостоящая операция всё равно блокирует единственный worker до завершения.

4. **Набор видимых/предзагружаемых страниц слишком широкий и может временно содержать несвязные старые страницы.** Используются `IntersectionObserver` с `rootMargin: '1200px 0px'` и удержание диапазона от `minVisible - 5` до `maxVisible + 5`. При быстрых прыжках старые страницы остаются в наборе достаточно долго, чтобы поставить или завершить ненужные задачи.

5. **Текстовый слой конкурирует с растровым рендером.** Для каждой видимой страницы одновременно вызываются `renderPage()` и `renderTextLayer()`, хотя пользователю сначала нужны пиксели актуальной страницы.

6. **Использован только низкоуровневый engine, а не готовый EmbedPDF viewer.** Производительность `app.embedpdf.com` обеспечивается не одним PDFium: готовый viewer заявляет виртуализированную прокрутку и собственное планирование. Текущая миграция сохранила самописный layout Book Hub и заменила только исполнитель рендера.

### Range-загрузка

`pdfFixedLayoutAdapter.ts` передаёт `mode: 'range-request'`, а `docs/APP.md` утверждает, что PDF загружаются range-запросами. Это неверно для `@embedpdf/engines` 2.15.0.

Официальная документация `openDocumentUrl` прямо указывает, что текущая реализация всегда делает полный `fetch` и `response.arrayBuffer()`, а параметр `mode` зарезервирован на будущее: <https://www.embedpdf.com/docs/engines/document-lifecycle/open-document-url>.

Backend менять ради Range не требуется: `backend/internal/httpapi/book_handlers.go` использует `http.ServeFile`, и фактический ответ уже содержит `Accept-Ranges: bytes`. Ограничение находится в клиентской библиотеке.

Range влияет на первоначальное открытие 190-МБ файла, но не объясняет задержку после пролистывания уже открытого документа. Сначала исправить рендер и очередь, затем отдельно решать startup loading.

## Архитектурное решение

Для этой задачи сохранить существующую Book Hub читалку и заменить full-page raster pipeline на **viewport-driven тайловый рендер с ограниченным бюджетом и latest-viewport scheduler**.

Интеграцию `@embedpdf/snippet` или полного готового viewer не выполнять в рамках этой задачи: она потребует заново интегрировать общий fixed-layout UX, настройки ширины, прогресс, историю, фильтры, поиск и боковые панели. Это допустимо только как отдельное архитектурное решение.

### Основные инварианты

- `<section data-page-number>` сохраняет полную CSS-ширину и CSS-высоту страницы. Поэтому размеры документа, прогресс чтения и scroll anchors не зависят от наличия растровых тайлов.
- Растровые поверхности создаются только для видимого участка страницы и небольшого вертикального overscan.
- Ни один canvas не превышает единый pixel budget.
- При смене viewport новые задачи получают приоритет над ещё не запущенными старыми задачами.
- Уже начавшаяся задача может блокировать worker только на время рендера одного ограниченного тайла, а не страницы высотой 23 тысячи пикселей.
- Результат с устаревшим generation token никогда не попадает в DOM.
- Текст и поиск остаются page-coordinate слоями и не зависят от разбиения растра на тайлы.
- Включённые фильтры обрабатывают только те же активные тайлы; полный filtered canvas страницы не создаётся.

### Рекомендуемые новые модули

Названия можно скорректировать по ближайшему паттерну, но обязанности разделить явно:

1. `frontend/src/components/common/PdfReader/pdfRenderPlan.ts`
   - чистые типы и функции расчёта тайлов;
   - преобразование viewport/page geometry в PDF rectangles;
   - pixel budget, overscan и порядок приоритетов;
   - никаких DOM- и engine-вызовов.

2. `frontend/src/components/common/PdfReader/pdfRenderPlan.test.ts`
   - исчерпывающие тесты геометрии, DPR, tall pages, clipping и бюджета.

3. `frontend/src/components/common/PdfReader/pdfRenderScheduler.ts`
   - очередь уровня приложения поверх последовательного engine;
   - generation token;
   - отмена ещё не запущенных задач;
   - приоритет visible center → остальная видимая область → overscan → текст;
   - освобождение устаревших результатов и ресурсов.

4. `frontend/src/components/common/PdfReader/pdfRenderScheduler.test.ts`
   - fake engine tasks с управляемым завершением;
   - детерминированные проверки rapid jump и stale result.

Создавать отдельный Solid-компонент для тайлов только если он реально уменьшает ответственность `PdfReader.tsx`. Не переносить server state или book API в компонент.

### Начальные ограничения тайла

Значения должны быть константами и покрываться тестами. Рекомендуемая отправная точка:

- `maxTilePixels = 4_194_304` (4 MiPixels, около 16 МиБ RGBA);
- `maxTileDimension = 4096` либо меньшее подтверждённое ограничение canvas/WebGL;
- вертикальный overscan — один viewport, но также ограниченный числом тайлов и общим pixel budget;
- DPR по-прежнему ограничивать существующим `maxRenderPixelRatio = 2`;
- для обычной страницы, целиком помещающейся в budget, разрешён fast path одним тайлом.

Это стартовые значения, а не догма. Финальные значения выбрать по тестам на desktop DPR 1/2 и узком viewport. Критичен проверяемый верхний предел, а не конкретное число.

### Геометрия `renderPageRectRaw`

Установленный API поддерживает:

```ts
renderPageRectRaw(
  document,
  page,
  rect: { origin: { x, y }, size: { width, height } },
  options,
)
```

`rect` задаётся в PDF coordinate space, а размер результата равен размеру rect, умноженному на `scaleFactor` и DPR. Адаптер сейчас открывает документ с `normalizeRotation: true`.

Перед основной реализацией создать минимальный contract test/throwaway probe с PDF, содержащим цветные верхнюю и нижнюю полосы. Он должен однозначно определить направление оси Y, clipping, rotation и поведение `withAnnotations`/`withForms`. Не угадывать преобразование координат по DOM.

### Тайлы и DOM

Для каждой страницы:

- section остаётся full-size placeholder;
- внутри находится абсолютно позиционированный контейнер растровых тайлов;
- каждый тайл знает PDF rect, CSS top/left/width/height, render scale, generation и filter key;
- canvas тайла имеет ограниченный внутренний размер и CSS-размер соответствующего участка страницы;
- ушедшие за active window тайлы удаляются либо обнуляются немедленно;
- повторный приход в ту же область может использовать небольшой LRU только в пределах общего бюджета; начинать без LRU проще и безопаснее;
- resize, смена DPR, автоширины или увеличения ширины создают новую generation и новый render plan с сохранением scroll anchor.

Не создавать по одному пустому `<canvas>` на каждую страницу заранее, если это больше не нужно. Page sections должны существовать для layout/navigation, а тяжёлые поверхности — только для active window.

### Планировщик

Планировщик обязан учитывать ограничение `@embedpdf/engines`:

- одновременно выполняется одна engine operation;
- cancel queued task работает, cancel already running task не останавливает underlying PDFium operation;
- поэтому ограниченный размер каждого тайла является частью корректности scheduler, а не только оптимизацией памяти.

Поведение при scroll/jump:

1. На каждом coalesced update (не чаще одного `requestAnimationFrame`) вычислить актуальный viewport и новый generation.
2. Удалить из очереди все не начатые bitmap/text/filter tasks предыдущего plan.
3. Сначала поставить тайл, пересекающий центр viewport, затем остальные видимые тайлы, затем overscan.
4. Не ставить text task, пока хотя бы один видимый bitmap tile страницы не показан.
5. Text tasks и поиск имеют более низкий приоритет и должны удаляться при уходе страницы.
6. Завершившийся stale task освобождает результат без записи в canvas.
7. Рендер соседних страниц не должен задерживать первый тайл текущей страницы.

Не использовать `minVisible..maxVisible` как диапазон удержания: transient-набор может быть несвязным. Active window строить от текущей геометрии viewport, а не от исторического минимума и максимума callback-событий.

`IntersectionObserver` можно оставить только как сигнал пересчёта, но источником истины должен быть актуальный viewport/page geometry. Альтернатива — вычислять пересечения на scroll через `requestAnimationFrame`. Выбрать один источник истины и покрыть rapid-jump тестом.

### Фильтры

Текущее `pdfWebglFilter.ts` тайлит GPU-обработку, но принимает полный source и target canvas. После перехода на viewport tiles:

- фильтровать каждый активный raster tile отдельно;
- для фильтров с выборкой соседних пикселей рендерить расширенный rect с overlap, применять фильтр и копировать в DOM только центральную часть;
- сохранить эквивалент существующего `filterSamplingOverlap` и проверить отсутствие швов на границах;
- не создавать полный filtered canvas страницы;
- изменение цепочки фильтров инвалидирует filtered variant активных тайлов, но не требует повторного PDFium-рендера исходного тайла;
- выключенные фильтры не создают дополнительные canvas;
- при ошибке WebGL сохранить текущее graceful degradation и исходное изображение.

Добавить визуальную/пиксельную проверку границы тайлов для инверсии и хотя бы одного convolution-подобного text enhancement filter.

### Текстовый слой и поиск

- Геометрия `PdfTextRectObject` остаётся в координатах всей страницы и масштабируется в CSS как сейчас.
- Text layer может оставаться одним DOM-слоем страницы, но создавать его только для актуальной страницы/active window.
- Поиск по всей книге не менять функционально.
- После навигации к результату сначала показать bitmap tile цели, затем подсветку и текст.
- При удалении raster tiles не удалять search state; при удалении page text layer его можно восстановить из cache либо повторно извлечь после bitmap с низким приоритетом.
- Проверить выделение/копирование текста на границе двух raster tiles: raster splitting не должен влиять на selection DOM.

## Порядок реализации

### Этап 1. Зафиксировать красный сигнал

1. Добавить синтетический tall-page PDF в mocked E2E API. Не добавлять реальный 190-МБ файл или пользовательскую книгу в репозиторий.
2. Fixture должна иметь несколько страниц с большой высотой и различимым содержимым/цветными полосами. Генератор обязан вычислять корректные xref offsets, а не поддерживать их вручную после каждого изменения.
3. Добавить структурный E2E-тест быстрого перехода через несколько страниц к дальней цели.
4. До исправления тест должен ловить хотя бы одно из текущих нарушений:
   - canvas превышает pixel budget;
   - после rapid jump остаются raster surfaces старых страниц;
   - целевая страница ждёт очередь промежуточных рендеров.

**Критерий завершения:** одна агент-запускаемая команда стабильно воспроизводит именно накопление лишних PDF-render tasks или превышение canvas budget.

### Этап 2. Чистая геометрия и budget

1. Реализовать и протестировать pure render plan.
2. Проверить DPR 1 и 2, обычные и экстремально высокие страницы, частично видимую страницу, overscan, clipping и resize.
3. Добавить adapter method для `renderPageRectRaw`.
4. Подтвердить ось Y и rotation contract отдельной fixture.

**Критерий завершения:** ни один рассчитанный output tile не превышает dimension/pixel budget; union core rects покрывает требуемую видимую область без дыр и выхода за page bounds.

### Этап 3. Viewport tiles и scheduler

1. Перевести bitmap rendering с full-page canvas на тайлы.
2. Ввести generation и latest-viewport priority.
3. Освобождать offscreen tiles и игнорировать stale results.
4. Удалить зависимость retention от `minVisible..maxVisible`.
5. Сохранить scroll anchor при resize/изменении ширины.

**Критерий завершения:** rapid-jump E2E становится зелёным; первый tile страницы 40 появляется без ожидания рендера всех промежуточных страниц; суммарная площадь canvas ограничена.

### Этап 4. Текст, поиск, фильтры и edge cases

2. Восстановить/подтвердить поиск, подсветку и selection.

**Критерий завершения:** все существующие PDF E2E проходят, новые тесты фильтров/тайлов проходят, между тайлами нет видимых швов, функции reader chrome не регрессировали.

### Этап 5. Startup loading и документация

1. Проверить release notes и фактический код самой новой совместимой версии `@embedpdf/engines`.
2. Обновлять библиотеку ради Range только если реализация действительно делает `Range` requests и может открыть документ до полного скачивания. Проверить это Network-тестом с ответами `206`, а не наличием опции в типах.
3. Если Range всё ещё не реализован, оставить full fetch и удалить/не использовать вводящий в заблуждение `mode: 'range-request'` либо снабдить его точным комментарием о неработающем reserved option.

## Автоматические тесты

### Unit

Обязательные сценарии `pdfRenderPlan.test.ts`:

- обычная страница помещается в один tile;
- страница с пропорциями `768.96 × 12800`, display width около 1400, DPR 1/2;
- tile dimensions и pixel count всегда в budget;
- viewport в начале, середине и конце страницы;
- overscan обрезается page bounds;
- resize/zoom меняют key/generation;
- соседние core rects не имеют дыр и лишнего overlap;
- PDF→CSS и CSS→PDF преобразования обратимы с разумной погрешностью;
- rotation-normalized contract.

Обязательные сценарии scheduler test:

- последовательность targets 12 → 20 → 28 → 36 → 40 запускает latest target раньше не начатых stale targets;
- already-running stale tile может закончиться, но не записывает результат и задерживает цель не более стоимости одного tile;
- queued stale bitmap/text tasks удаляются;
- text task не стартует раньше первого bitmap актуальной страницы;
- смена filter key не запускает повторный PDF render исходного актуального tile;
- release удаляет canvas/buffers и object URLs, если они появятся;
- повторное завершение/abort не ломает счётчики queue.

### Playwright E2E

Расширить `frontend/tests/pdf-reader.spec.ts`:

- tall PDF отображает первые пиксели;
- rapid page jumps приводят к целевой странице;
- ни один canvas не превышает budget;
- raster canvases ушедших страниц удалены или имеют нулевой размер;
- total allocated pixel area не превышает заданный предел;
- автоширина и увеличение ширины сохраняют scroll anchor;
- оглавление и browser back/forward продолжают работать;
- поиск, highlight и selection работают после перехода;
- включение инверсии и text enhancement не создаёт швов;
- resize и DPR не оставляют старые raster surfaces.

В CI отдавать предпочтение структурным ограничениям, а не жёстким миллисекундам: timing assertions на shared runners нестабильны. Временной benchmark выполнять отдельно на одной машине.

## Performance acceptance

На одной и той же машине и браузере выполнить не менее пяти прогонов после cold page load и отдельно после warm engine load. Фиксировать медиану и худший результат.

Для «хакер 322» при viewport `1440 × 900`:

- rapid sequence 12 → 20 → 28 → 36 → 40: первые пиксели страницы 40 — медиана не более 1 секунды, ни один прогон не более 2 секунд;
- улучшение относительно зафиксированного baseline 4,2–5,6 секунды — минимум в 3 раза по медиане;
- прямой переход на страницу 40 не должен стать медленнее baseline 1,21–1,25 секунды до первых пикселей;
- один canvas не превышает выбранный tile budget;
- суммарная площадь активных исходных canvas без фильтров соответствует не более примерно 128 МиБ RGBA; с фильтрами — не более примерно 256 МиБ. Проверять через сумму `canvas.width * canvas.height * 4`, понимая, что это нижняя оценка реальной памяти;
- после стабилизации viewport растры далёких промежуточных страниц отсутствуют;
- не должно быть long task, вызванного одним `putImageData` полного canvas высотой десятки тысяч пикселей.

Если реальная книга больше недоступна, использовать synthetic tall PDF для регрессии, но финальную ручную приёмку всё равно попросить выполнить владельца на «хакер 322». Локальные учётные данные и содержимое книги в репозиторий не записывать.

## Нефункциональные ограничения

- Не менять API/backend в рамках viewport rendering: HTTP-контракт для этого не требуется.
- Не редактировать `frontend/src/api/generated/schema.ts` вручную.
- Не смешивать миграцию полного EmbedPDF viewer, unrelated refactoring или изменения DJVU с этой задачей.
- Сохранять TypeScript strictness и SolidJS reactive patterns.
- Не хранить engine/server state в page component, если его можно изолировать в PDF rendering module.
- Не менять пользовательское определение автоширины: CSS-страница по-прежнему занимает доступную ширину. Оптимизируется растр, а не layout.
- Не ухудшать качество обычных PDF ради tall-page случая: budget достигается тайлами, а не постоянным low-resolution upscale.
- Не считать скрытый canvas освобождённым: для тяжёлой поверхности требуется удалить ссылку или установить `width = height = 0`.
- Любая временная instrumentation должна иметь уникальный префикс и быть удалена перед завершением.

## Риски и обязательные проверки

- **Ось Y PDF rect.** Подтвердить fixture; ошибка даст перевёрнутые/смещённые тайлы.
- **Rotation.** `normalizeRotation: true` уменьшает варианты, но rotated PDF всё равно нужен в тесте.
- **Швы фильтров.** Для соседних выборок нужен overlap и crop центральной области.
- **Forms/annotations.** Сохранить `withAnnotations: true` и `withForms: true` в rect rendering и проверить clipping.
- **Retina/DPR.** Pixel budget должен ограничивать итоговый output после DPR.
- **Canvas/WebGL limits.** Учитывать фактический `MAX_TEXTURE_SIZE`, но не полагаться на него как на единственный memory budget.
- **Scroll progress.** Tile mount/unmount не должен менять CSS-высоту page section и общий `scrollHeight`.
- **Resize races.** Старое поколение не должно перезаписать тайл после изменения ширины.
- **Shared engine.** Закрывать документ, но не уничтожать singleton engine, используемый извлечением обложек.
- **Search all pages.** Не позволять длительному поиску блокировать актуальный bitmap без явной политики приоритетов/отмены.
- **Browser history.** Page jump, back и forward должны восстанавливать корректный viewport до загрузки raster tiles.
