# Book Hub

Book Hub — персональный self-hosted-архив книг с удобной возможностью чтения в браузере.

## Установка

Скачайте проект и перейдите в его каталог:

```bash
git clone https://github.com/avin/book-hub.git
cd book-hub
```

Создайте файл настроек:

```bash
make env
```

Откройте `.env`, задайте обязательный `BOOK_HUB_DATABASE_URL` и замените `BOOK_HUB_SESSION_SECRET`.
Выберите одну из СУБД:

- PostgreSQL: оставьте пример URL, замените `POSTGRES_PASSWORD` и пароль в URL одинаковым значением.
- SQLite: установите `BOOK_HUB_DATABASE_URL=sqlite:///data/db/book-hub.sqlite`. Переменные `POSTGRES_*` можно удалить;
  контейнер PostgreSQL не запускается. База хранится в отдельном постоянном volume `sqlite_data`.

SQLite поддерживает одного работающего backend на локальном диске сервера и несколько одновременно работающих
пользователей. Для нескольких экземпляров backend используйте PostgreSQL. Переход между СУБД не переносит данные.
При необходимости до запуска измените
`BOOK_HUB_PUBLIC_PORT`. `BOOK_HUB_HTTP_ADDR` — внутренний адрес backend; в Docker он должен быть в формате
`:порт` (например, `:38080`).

## Запуск

### Локальная сборка

Соберите образы из исходного кода на этом сервере, примените миграции и запустите приложение:

```bash
make local-deploy
```

Make выбирает `docker-compose.yml` для PostgreSQL или `docker-compose.sqlite.yml` для SQLite по URL подключения;
локальный `docker-compose.override.yml` при развёртывании не применяется. Перед миграциями приложение останавливается,
после успешного обновления запускается. При ошибке миграций оно остаётся остановленным.

Проверьте готовность:

```bash
make health-http
```

Откройте `http://адрес-сервера:8080/` или используйте выбранный в `.env` порт.

### Готовые образы

Этот режим не собирает проект на сервере. Для обычной установки укажите `latest`; при необходимости закрепить конкретную
версию вместо него укажите её тег:

```bash
make ghcr-deploy BOOK_HUB_IMAGE_TAG=latest
```

`docker-compose.ghcr.yml` заменяет локальную сборку готовыми образами поверх выбранного файла стека.
Образ frontend сейчас собран с `BOOK_HUB_BASE_PATH=/`; не меняйте этот параметр при запуске
готового образа.

При прямом запуске Compose указывайте нужные файлы. Пример SQLite с локальной сборкой:

```bash
docker compose -f docker-compose.sqlite.yml build
docker compose -f docker-compose.sqlite.yml stop backend frontend
docker compose -f docker-compose.sqlite.yml run --rm migrate up
docker compose -f docker-compose.sqlite.yml up -d
```

Для PostgreSQL используйте `docker-compose.yml` (обычный `docker compose up` также сохраняется).
Для GHCR добавьте `-f docker-compose.ghcr.yml` и задайте `BOOK_HUB_IMAGE_TAG`. Миграции не выполняются автоматически
при старте сервера. Сервер и admin CLI требуют актуальную завершённую схему; SQLite-файл создаётся только мигратором.

## Кэш файлов книг

Кэш по умолчанию выключен. Чтобы хранить оригиналы на HDD, а повторно открываемые книги — на SSD, укажите,
например, `BOOK_HUB_BOOKS_DIR=/mnt/hdd/books`, `BOOK_HUB_CACHE_DIR=/mnt/ssd/book-cache` и
`BOOK_HUB_CACHE_MAX_BYTES=10737418240` (10 ГиБ). Для удалённого хранилища настраивается та же пара параметров кэша.
Пути должны быть доступны пользователю backend; в Compose подключите соответствующие диски как volumes.
Оба Compose-стека отдельно монтируют `/data/cache` и рабочий каталог по умолчанию `/data/books/tmp`
в anonymous volumes каждого backend. Они сохраняются при перезапуске и обычном пересоздании контейнера;
`down` с последующим новым `up` или обновление с `--renew-anon-volumes` создаёт новые пустые копии.
Для включения такого кэша достаточно выбрать `BOOK_HUB_CACHE_DIR=/data/cache` и его лимит.
Для постоянного SSD-каталога замените соответствующий mount backend на bind mount; при нескольких backend
каждый получает собственные cache/work mounts. Admin, backup и мигратор не подключают эти volumes.
Оригиналы и локальные изображения в `book_storage` остаются общими. Новые bind-каталоги должны быть доступны
пользователю `bookhub`; каталог произвольного пользовательского пути Compose автоматически не подготавливает.
Каталоги оригиналов, изображений, рабочих файлов и кэша должны быть раздельными, без вложения друг в друга.

Кэш использует LRU, защищает текущие выдачи и учитывает готовые и получаемые файлы в общем строгом лимите.
Завершённые копии сохраняются после перезапуска. Повторная выдача и проверка готовности не обращаются к оригиналам,
поэтому не требуют пробуждения HDD. При недоступных оригиналах уже кэшированные книги остаются доступны владельцам.
Неисправность или заполнение кэша допускает получение оригинала: локального напрямую, удалённого через рабочий
каталог с отдельным лимитом (по умолчанию 1 ГиБ). Место для него требуется сверх лимита кэша.
Ошибка кэша отражается в логе и не отменяет успешную загрузку книги.

Каждому backend нужен собственный каталог и лимит кэша; общая директория кэша между процессами не поддерживается.
Удаление кэша при остановленном backend безопасно для библиотеки: единственный оригинал в нём не хранится.

Для нескольких backend используйте общую PostgreSQL-базу и одинаковые параметры хранилища оригиналов и сессий.
Локальный каталог изображений должен быть доступен для чтения и записи всем обслуживающим их экземплярам;
отдельные кэши не заменяют общий доступ к обложкам и миниатюрам. У каждого backend должны быть собственные
`BOOK_HUB_WORK_DIR`, `BOOK_HUB_WORK_MAX_BYTES`, `BOOK_HUB_CACHE_DIR` и `BOOK_HUB_CACHE_MAX_BYTES`.
Получения одного файла объединяются внутри экземпляра; состояние очереди удаления и защита используемых
оригиналов согласуются через БД. Перезапуск или очистка одного кэша не требует очистки остальных.
SQLite по-прежнему поддерживает только один backend.

## Нехватка памяти при локальной сборке

На VPS с небольшим объёмом RAM сборка Go backend и frontend может завершиться ошибкой `out of memory`, `Killed` или с
кодом `137`. Проверьте память и свободное место на диске:

```bash
free -h
df -h /
```

Если на диске достаточно свободного места, один раз создайте постоянный swap-файл размером 4 GB:

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Убедитесь, что swap подключён, затем повторите `make local-deploy`:

```bash
free -h
make local-deploy
```

Swap снижает риск нехватки памяти, но делает сборку медленнее. Не создавайте его, если на системном диске недостаточно
свободного места.

## Первый пользователь

Откройте административную консоль:

```bash
make admin
```

Для запуска из GHCR используйте ту же команду с тегом образа:

```bash
make ghcr-admin BOOK_HUB_IMAGE_TAG=latest
```

В ней создайте пользователя. Созданный через консоль пользователь активен сразу:

```text
admin> create user
login: alice
password: надёжный-пароль
```

Команда `help` в этой консоли покажет остальные действия. Например, там можно изменить квоту пользователя, пароль или
статус аккаунта.

## Запуск без Docker и отдельного веб-сервера

`book-hub-server` может раздавать готовый frontend вместе с API на `BOOK_HUB_HTTP_ADDR`.
Укажите `BOOK_HUB_FRONTEND_DIR`: абсолютный путь к сборке либо путь относительно рабочего каталога процесса.
Пустое или отсутствующее значение сохраняет режим только API; Docker/Compose по умолчанию используют отдельный frontend/nginx.

На машине сборки нужны Go, Node.js и npm из [инструкции разработки](DEV.md). Пример для Linux:

```bash
mkdir -p dist/bin
CGO_ENABLED=0 go -C backend build -o ../dist/bin/book-hub-server ./cmd/book-hub-server
CGO_ENABLED=0 go -C backend build -o ../dist/bin/book-hub-migrate ./cmd/book-hub-migrate
CGO_ENABLED=0 go -C backend build -o ../dist/bin/book-hub-admin ./cmd/book-hub-admin
npm --prefix frontend ci
VITE_BASE_PATH=/ npm --prefix frontend run build
```

Для другого устройства задайте подходящие `GOOS`, `GOARCH` и, при необходимости, `GOARM`.
Перенесите три бинарника из `dist/bin/` и содержимое `frontend/dist/` на устройство, например
в `/opt/book-hub/bin/` и `/opt/book-hub/frontend/`. На устройстве для работы не нужны Docker, Node.js или Go.
Миграции входят в бинарник мигратора; копировать SQL-файлы отдельно не требуется.

Перед каждым запуском экспортируйте настройки в окружение процесса или задайте их в менеджере служб.
Бинарники сами не читают `.env`. Пример с SQLite и отдельными каталогами на USB:

```bash
mkdir -p /mnt/usb/book-hub/{db,images,work}
export BOOK_HUB_DATABASE_URL=sqlite:///mnt/usb/book-hub/db/book-hub.sqlite
export BOOK_HUB_SESSION_SECRET='replace-with-a-random-secret-at-least-32-characters'
export BOOK_HUB_BOOK_STORAGE=directory
export BOOK_HUB_BOOKS_DIR=/mnt/raid/book-hub/books
export BOOK_HUB_IMAGES_DIR=/mnt/usb/book-hub/images
export BOOK_HUB_WORK_DIR=/mnt/usb/book-hub/work
export BOOK_HUB_HTTP_ADDR=:8080
export BOOK_HUB_BASE_PATH=/
export BOOK_HUB_FRONTEND_DIR=/opt/book-hub/frontend
export BOOK_HUB_REGISTRATION_ENABLED=false
```

SQLite должна находиться на локальном диске; одновременно запускается один backend.
Пользователь службы должен иметь доступ на запись к БД, книгам, изображениям и рабочему каталогу,
а к frontend достаточно доступа на чтение. Значение секрета в примере обязательно замените.

Сначала примените миграции:

```bash
/opt/book-hub/bin/book-hub-migrate up
```

Затем создайте пользователя:

```bash
/opt/book-hub/bin/book-hub-admin
```

В консоли введите `create user`, укажите логин и пароль, затем `quit`. После этого запустите сервер:

```bash
/opt/book-hub/bin/book-hub-server
```

Откройте `http://адрес-устройства:8080/`. Страницы и API доступны на одном адресе, API остаётся под `/api`.
Для размещения под `/hub` соберите frontend с `VITE_BASE_PATH=/hub`, задайте `BOOK_HUB_BASE_PATH=/hub`
и откройте `/hub/`; API будет под `/hub/api`. В каталоге сборки `index.html` остаётся непосредственно в корне,
без вложенной папки `hub`. Сервер не переписывает пути внутри сборки и не собирает frontend при запуске.

Каталог frontend целиком публичный: указывайте только production-сборку. Не размещайте в нём книги,
изображения приложения, БД, конфигурацию, рабочие файлы или кэш. Просмотр каталогов, скрытые файлы
и ссылки за пределы сборки запрещены. Неверный или нечитаемый каталог либо отсутствие обычного читаемого
`index.html` завершают запуск ошибкой; мигратор, admin и backup CLI от frontend не зависят.

HTML всегда загружается заново, ресурсы Vite с хэшем в имени могут кэшироваться надолго,
остальные файлы требуют перепроверки. Обновляйте сборку с перезапуском сервера. Чтобы вернуться к внешнему
веб-серверу, удалите `BOOK_HUB_FRONTEND_DIR` из окружения и перезапустите backend.
HTTPS настраивается внешним TLS-прокси; при HTTPS задайте `BOOK_HUB_COOKIE_SECURE=true`.
Размещение frontend на USB само по себе не гарантирует сон HDD: он зависит и от расположения остальных данных и служб.

## Обычные действия

| Задача                        | Команда                                                                  |
|-------------------------------|--------------------------------------------------------------------------|
| Статус сервисов               | `make ps`                                                                |
| Журнал всех сервисов          | `make logs`                                                              |
| Журнал одного сервиса         | `make logs SERVICE=backend`                                              |
| Перезапуск                    | `make docker-restart`                                                    |
| Развернуть локальную сборку   | `make local-deploy`                                                      |
| Развернуть готовые GHCR-образы | `make ghcr-deploy BOOK_HUB_IMAGE_TAG=latest`                              |

После изменения настроек в `.env` запустите тот же режим развертывания, которым пользуетесь: `make local-deploy` или
`make ghcr-deploy BOOK_HUB_IMAGE_TAG=latest`.

Если приложение открыто через HTTPS, установите `BOOK_HUB_COOKIE_SECURE=true`. Размещение в подпапке сайта через
`BOOK_HUB_BASE_PATH` поддерживается при локальной сборке; для GHCR нужен образ frontend, собранный с нужным base path.

## Файлы книг и рабочая директория

Настройки применяются после перезапуска backend. Для всей библиотеки выбирается одно хранилище оригиналов;
локальный вариант — `BOOK_HUB_BOOK_STORAGE=directory`.

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `BOOK_HUB_BOOKS_DIR` | `BOOK_HUB_STORAGE_DIR/books` | Целые исходные файлы книг |
| `BOOK_HUB_IMAGES_DIR` | `BOOK_HUB_STORAGE_DIR/covers` | Локальные обложки и миниатюры |
| `BOOK_HUB_WORK_DIR` | `BOOK_HUB_STORAGE_DIR/tmp` | Временные загрузки и получение оригиналов |
| `BOOK_HUB_WORK_MAX_BYTES` | `1073741824` | Общий рабочий лимит 1 ГиБ на backend |

Существующая установка продолжает использовать прежние пути без переноса. Для отдельных дисков задайте
непересекающиеся каталоги: например, оригиналы на HDD, изображения и рабочие файлы на SSD. В Compose оба стека
передают настройки через `.env`; подключите выбранные каталоги как volumes ко всем применимым сервисам
`backend`, `admin`, `backup` и `migrate`. Каталоги должны быть доступны пользователю `bookhub` внутри контейнера.
Каждому backend нужен собственный рабочий каталог и бюджет; место резервной копии учитывается отдельно.

При заполненном рабочем бюджете новая загрузка или получение возвращает временную ошибку, текущие выдачи
продолжаются. Удалённый оригинал полностью проверяется по размеру и SHA-256 перед выдачей, локальный файл
проверяется и выдаётся напрямую. Недоступность оригиналов не блокирует запуск и периодическую проверку готовности.

Для FTP задайте `BOOK_HUB_BOOK_STORAGE=ftp`, `BOOK_HUB_FTP_ADDR=ftp.example.org:21`,
`BOOK_HUB_FTP_USER`, `BOOK_HUB_FTP_PASSWORD` и `BOOK_HUB_FTP_ROOT=/book-hub`.
Корень — абсолютная выделенная директория внутри FTP-аккаунта, отличная от `/`; Book Hub создаёт подкаталоги
и управляет только файлами этой области. Передача использует пассивный режим: разрешите подключения backend
к управляющему и пассивным портам сервера. Обычный FTP передаёт учётные данные и книги без TLS.
Обложки, миниатюры и рабочая директория остаются локальными; FTP не требует volume с оригиналами.
Настройки передаются backend и административным инструментам через тот же `.env` в обоих Compose-стеках.
Успех загрузки подтверждается после публикации целого оригинала и записи библиотеки. Ошибки подключения,
входа или передачи возвращают временную ошибку; незавершённый оригинал не выдаётся как книга.

Для explicit FTPS выберите `BOOK_HUB_BOOK_STORAGE=ftps-explicit` (обычно порт 21),
для implicit FTPS — `ftps-implicit` (обычно порт 990). Адрес с портом задаётся явно в
`BOOK_HUB_FTP_ADDR`; остальные параметры FTP общие. Оба режима шифруют управляющее
соединение и передачу файлов, проверяют сертификат и имя сервера. При необходимости
задайте `BOOK_HUB_FTP_CA_FILE` с PEM дополнительных доверенных CA. Файл должен быть
доступен серверу и CLI (в контейнерах его нужно смонтировать по указанному пути).
Ошибки TLS не вызывают перехода на незашифрованный FTP. Недоступность сервера допускается
при запуске, а некорректный или недоступный файл CA отклоняется при создании подключения.

Для S3 задайте `BOOK_HUB_BOOK_STORAGE=s3`, `BOOK_HUB_S3_REGION`, `BOOK_HUB_S3_BUCKET`,
`BOOK_HUB_S3_ACCESS_KEY_ID`, `BOOK_HUB_S3_SECRET_ACCESS_KEY` и выделенный `BOOK_HUB_S3_PREFIX`
(по умолчанию `books`). Бакет создаёт администратор; Book Hub управляет только ключами внутри этого
префикса. Для Amazon S3 оставьте `BOOK_HUB_S3_ENDPOINT` пустым. Для совместимого сервиса укажите HTTP(S)
origin, например `https://s3.example.org`; в этом случае используется path-style адресация.
Проверен Garage v2.5.0, включая загрузку частями и отмену; совместимость остальных сервисов требует проверки.
Учётной записи нужны чтение, запись, удаление и листинг выделенного префикса, а также multipart-операции
и удаление незавершённых частей. Учётные данные остаются на сервере. Backend не проверяет доступность
S3 при запуске и не выдаёт браузеру прямые ссылки. Изображения остаются локальными.

## Резервная копия и восстановление

Создайте полную резервную копию базы и файлов книг:

```bash
make backup
```

Для установки из GHCR добавляйте `BOOK_HUB_IMAGE_TAG` с используемым тегом к командам backup и restore.
Команда выведет каталог созданной копии, например `./backups/20260712-120000`. Скопируйте этот каталог с сервера в
надёжное место.

Восстановление заменяет БД и размещает оригиналы в пустой выделенной директории. Укажите каталог копии:

```bash
make restore BACKUP=./backups/20260712-120000
```

Копия содержит `manifest.json` (версия формата, СУБД и версия схемы), `database.sql` для PostgreSQL или
`database.sqlite` для SQLite, а также `storage.tar.gz` с книгами и обложками. SQLite-снимок включает подтверждённые
данные из WAL. Старый набор `database.sql` + `storage.tar.gz` без manifest продолжает восстанавливаться в PostgreSQL.
Оригиналы и локальные изображения входят в копию даже при размещении в разных каталогах; рабочие файлы
и кэш не включаются. Размер и SHA-256 каждой необходимой книги проверяются при backup и restore.
Восстановление в другую СУБД, повреждённая копия и непустая область оригиналов отклоняются до изменения
назначения. Поддерживаются прежние абсолютные и относительные пути и старые архивы со служебными записями;
при восстановлении ссылки БД пересчитываются под текущие настройки оригиналов и изображений.
Каталог резервных копий и локальные каталоги оригиналов, изображений, рабочих файлов и кэша не должны
содержать друг друга; SQLite-файл должен находиться
за пределами обоих каталогов. Небезопасное размещение отклоняется до изменения данных.
Для PostgreSQL используются утилиты той же основной версии, что и сервер; Docker-образ включает клиенты 16 и 17.

Обе команды останавливают backend и frontend и запускают их после успеха. При ошибке после остановки приложение
остаётся выключенным. При сбое или прерывании restore очистите только выделенное назначение оригиналов
и повторите восстановление из той же копии; автоматического продолжения и отката нет. Поддерживаемая старая
схема обновляется штатными миграциями в процессе restore до запуска сервера. На время миграций, backup и restore не запускайте другие операции
записи через admin CLI или второй мигратор. Volumes сохраняются после `make docker-down`; не удаляйте их через `down -v`.

Для смены хранилища оригиналов выполните `make backup`, измените `BOOK_HUB_BOOK_STORAGE` и параметры
выбранной директории, FTP, explicit/implicit FTPS или S3. При необходимости измените `BOOK_HUB_IMAGES_DIR`
и подключённые volumes, затем выполните `make restore`. Команды backup и restore используют те же настройки
хранилища, что и backend. Директория или выделенный FTP/FTPS-каталог либо S3-префикс назначения должны быть
пустыми. Приложение не очищает весь FTP-сервер или бакет; соседние области не затрагиваются.
Полная копия получает оригиналы из основного хранилища даже при наличии кэша; повреждённый или недоступный
необходимый оригинал не даёт создать успешную копию. После успешного backup исходный сервис не требуется.
После backup приложение автоматически запускается: учитывайте возможные новые записи между копированием
и перенастройкой. Место для полного архива и временной распаковки требуется отдельно от рабочего лимита backend.
Backup CLI читает те же параметры хранения, что и сервер, и не требует `BOOK_HUB_SESSION_SECRET`.
