# Опциональная раздача frontend из Go-сервера

Status: resolved

## Problem Statement

Для установки Book Hub на NAS и микрокомпьютеры администратору сейчас требуется отдельный веб-сервер, который раздаёт собранный frontend и передаёт запросы к API в Go backend. На устройствах с ограниченной памятью и нестандартной прошивкой это усложняет установку: приходится устанавливать дополнительную службу либо изменять конфигурацию встроенного веб-сервера, которая может восстанавливаться из образа прошивки при перезагрузке.

Администратору нужен способ запустить интерфейс и API одним Go-процессом, указав каталог готовой сборки frontend. При этом существующие установки с nginx, Apache или другим внешним веб-сервером должны продолжать работать без перенастройки.

## Solution

Добавить необязательную настройку `BOOK_HUB_FRONTEND_DIR`. Если она отсутствует или пуста, сервер сохраняет текущее поведение и обслуживает только API. Если указан каталог, тот же HTTP-сервер дополнительно раздаёт из него frontend на существующем адресе `BOOK_HUB_HTTP_ADDR`.

По умолчанию интерфейс доступен по `/`, а API остаётся под `/api`. При заданном `BOOK_HUB_BASE_PATH` интерфейс и API используют общий префикс. Администратор заранее собирает frontend для соответствующего префикса и переносит готовую сборку на устройство; Go-сервер ничего не собирает при запуске.

Каталог можно разместить на USB-накопителе отдельно от хранилища книг, базы данных, локальных изображений и рабочих файлов. Для работы этого режима отдельный процесс веб-сервера не требуется. Существующая схема запуска с внешним веб-сервером остаётся вариантом по умолчанию.

## User Stories

1. Как администратор микрокомпьютера, я хочу запустить интерфейс и API одним Go-процессом, чтобы установить Book Hub без отдельного веб-сервера.
2. Как владелец существующей установки, я хочу сохранить прежнее поведение при отсутствии новой настройки, чтобы обновление backend не требовало изменения развёртывания.
3. Как администратор, я хочу указать каталог готовой сборки через `BOOK_HUB_FRONTEND_DIR`, чтобы явно выбрать файлы, доступные через HTTP.
4. Как администратор, я хочу использовать абсолютный путь либо путь относительно рабочего каталога процесса, чтобы адаптировать запуск к устройству и его системе служб.
5. Как администратор NAS, я хочу хранить frontend на USB-накопителе, чтобы его выдача не требовала чтения с HDD.
6. Как пользователь, я хочу открыть корневой адрес сервера и получить интерфейс Book Hub, чтобы пользоваться приложением без дополнительного адреса или порта frontend.
7. Как пользователь, я хочу напрямую открыть или обновить страницу библиотеки, входа, настроек или читалки, чтобы сохранённые ссылки работали после перезапуска браузера.
8. Как пользователь, я хочу получать JavaScript, CSS, изображения и шрифты из сборки, чтобы интерфейс полностью работал через Go-сервер.
9. Как читатель PDF, я хочу получать ES-модули, worker, WASM-декодеры, CMap и стандартные шрифты с корректными типами содержимого, чтобы PDF-читалка работала в новом режиме.
10. Как читатель DJVU, я хочу получать ресурсы DjVu.js через тот же сервер, чтобы новый способ установки сохранял работу читалки DJVU.
11. Как читатель EPUB и FB2, я хочу сохранить работу адаптивной читалки, чтобы способ выдачи frontend не менял доступные форматы книг.
12. Как клиент API, я хочу сохранить адреса, методы, статусы и тела ответов API, чтобы включение frontend не нарушало интеграции и работу приложения.
13. Как клиент API, я хочу получать прежние ошибки для неизвестных API-адресов и неподдерживаемых методов, чтобы вместо ошибки неожиданно не получать HTML интерфейса.
14. Как пользователь, я хочу входить в аккаунт и выполнять действия с книгами через общий адрес интерфейса и API, чтобы авторизация, cookie и CSRF-защита продолжали работать.
15. Как администратор, я хочу разместить приложение под заданным `BOOK_HUB_BASE_PATH`, чтобы сохранить возможность установки в подпути.
16. Как администратор, я хочу, чтобы сервер не обслуживал frontend за пределами выбранного префикса, чтобы приложение не занимало посторонние адреса.
17. Как браузер, я хочу получать настоящий `404` для отсутствующих ресурсов, чтобы ошибка загрузки JavaScript, worker или WASM не маскировалась содержимым `index.html`.
18. Как пользователь, я хочу получать актуальный HTML после обновления frontend, чтобы старая оболочка приложения не мешала загрузке новой версии.
19. Как браузер, я хочу повторно использовать ресурсы с хэшем в имени, чтобы не загружать неизменившиеся файлы при каждом посещении.
20. Как HTTP-клиент, я хочу использовать `HEAD` для статических ресурсов, чтобы получать их заголовки без передачи тела ответа.
21. Как администратор, я хочу получить понятную ошибку запуска при неверном, недоступном или неполном каталоге frontend, чтобы сразу обнаружить ошибку пути или неподключённый накопитель.
22. Как владелец библиотеки, я хочу, чтобы статическая раздача не давала доступ к файлам за пределами каталога сборки, чтобы исходные файлы книг, база данных и настройки оставались защищёнными.
23. Как администратор, я хочу запретить просмотр содержимого каталогов и выдачу скрытых файлов, чтобы сервер публиковал только предназначенные для браузера ресурсы.
24. Как администратор устройства с малым объёмом RAM, я хочу передавать файлы без загрузки всей сборки в память, чтобы включение frontend не требовало значительного дополнительного объёма памяти.
25. Как администратор, я хочу запускать мигратор, admin CLI и резервное копирование без доступного frontend, чтобы обслуживание данных не зависело от каталога интерфейса.
26. Как администратор, я хочу отключить встроенную раздачу удалением новой настройки и перезапуском сервера, чтобы при необходимости вернуться к внешнему веб-серверу.
27. Как администратор, я хочу иметь документированный пример запуска с готовой сборкой и SQLite, чтобы установить Book Hub на устройство без Docker, Node.js и Go toolchain во время эксплуатации.

## Implementation Decisions

- Добавить серверную настройку `BOOK_HUB_FRONTEND_DIR`. Пустое или отсутствующее значение отключает раздачу frontend; дополнительных флагов включения не требуется. При выключенном режиме сервер не ищет сборку автоматически.
- Абсолютный путь используется напрямую; относительный разрешается относительно рабочего каталога процесса при запуске. Приведённый путь и доступ к каталогу подготавливаются один раз, без смены рабочего каталога процесса.
- Перед началом приёма HTTP-запросов проверить, что указанный каталог доступен для чтения и содержит доступный обычный файл `index.html`. Ошибка завершает запуск ненулевым кодом с понятным сообщением о настройке и причине. Не создавать каталог или пустую сборку автоматически и не переходить молча в режим только API.
- Проверка frontend относится к запуску HTTP-сервера. Общий загрузчик настроек файлового хранилища для административных команд не должен требовать наличия frontend, даже если новая переменная присутствует в общем окружении.
- Дополнить композицию публичного HTTP-обработчика: существующий обработчик API сохраняется, а выдача frontend подключается рядом с ним. В режиме frontend используется тот же listener и тот же процесс; отдельная служба, дополнительный HTTP-порт и reverse proxy не требуются.
- Сохранить приоритет точного API-префикса и его дочерних путей. Корень API, неизвестные API-маршруты и ошибки методов остаются в API-ветке и никогда не обрабатываются как страницы SPA. Сопоставлять префиксы по границам сегментов, не захватывая похожие имена.
- Сохранить существующие контракты API, авторизации, cookie, CSRF, идентификаторов запросов, проверок состояния, загрузки и выдачи исходных файлов книг. Новых API-операций и изменений схемы данных нет.
- Статические файлы и оболочка frontend доступны без серверной сессии, как при текущей раздаче внешним веб-сервером. Доступ к библиотеке и исходным файлам книг по-прежнему контролируется API; статическая раздача не заменяет эту проверку.
- При корневом `BOOK_HUB_BASE_PATH` раздавать frontend от `/`. При непустом префиксе раздавать его только внутри соответствующего подпути, а API — под тем же префиксом с суффиксом `/api`. Адрес самого префикса без завершающего слеша перенаправлять на вариант со слешем ответом `308`, сохраняя query string. За пределами префикса возвращать `404`.
- Каталог сборки содержит её обычное содержимое без дополнительной вложенной папки, повторяющей URL-префикс. Frontend должен быть заранее собран с `VITE_BASE_PATH`, соответствующим серверному `BOOK_HUB_BASE_PATH`; автоматическое переписывание HTML, JavaScript и путей внутри сборки не входит в решение.
- Существующий публичный файл выдаётся как файл. Для `GET` и `HEAD` на адреса страниц без файлового расширения использовать корневой `index.html`, если по этому адресу нет файла. Это поддерживает прямые переходы на текущие клиентские маршруты, включая читалку.
- Отсутствующий путь внутри каталогов ресурсов Vite, pdf.js и DjVu.js, а также отсутствующий путь с расширением файла возвращает `404`, даже если запрос допускает HTML. SPA-подстановка не применяется к API, скрытым файлам и запрещённым путям. Не возвращать HTML с кодом `200` вместо отсутствующего ресурса.
- Статическая ветка поддерживает `GET` и `HEAD`; прочие методы получают `405` с соответствующим `Allow` и не выполняют запись в каталог. Поведение методов API остаётся прежним.
- Использовать файловую выдачу стандартной библиотеки Go с потоковой передачей и стандартной поддержкой диапазонов и условных запросов там, где это совместимо с правилами кэширования. Не загружать всю сборку или большие файлы целиком в Go heap и не добавлять внешний runtime ради раздачи.
- Корректно задавать MIME-типы независимо от системной базы MIME на устройстве: JavaScript и `.mjs` должны иметь допустимый JavaScript MIME-тип, WASM — `application/wasm`, CSS — `text/css`, HTML — `text/html`. Остальные ресурсы читалок должны передаваться без преобразования содержимого.
- HTML оболочки, включая SPA-подстановку, выдавать с `Cache-Control: no-store, no-cache, must-revalidate` без ответа `304`, чтобы после обновления не оставался устаревший HTML. Успешные ресурсы Vite с хэшем в имени из каталога assets могут получать `public, max-age=31536000, immutable`. Остальные файлы выдавать с обязательной перепроверкой актуальности, без безусловного `immutable`. Ошибки статической раздачи не кэшировать.
- Ограничить доступ корнем настроенного каталога, включая URL-декодирование и символические ссылки. Запретить выход через `..`, ссылки наружу, выдачу специальных файлов, скрытых файлов и листинг каталогов. Корень сборки может сам находиться по символической ссылке; после его разрешения граница доступа остаётся внутри выбранной сборки.
- Назначение каталога — только публичная production-сборка. Не монтировать в статическую раздачу хранилище книг, локальные изображения приложения, БД, рабочую директорию, кэш файлов книг или конфигурацию с секретами. Доступ к приватным данным сохраняется через существующие API-операции.
- Чтение frontend не должно требовать обращения к хранилищу исходных файлов книг. Новая возможность не меняет действующие решения о SQLite/PostgreSQL, файловом хранилище и кэше файлов книг.
- Существующие Docker-образы и Compose-стеки по умолчанию сохраняют отдельный frontend. Не добавлять в них обязательный каталог frontend и не включать новый режим автоматически.
- Документировать настройку, относительные и абсолютные пути, соответствие URL-префиксов, правила публичности каталога и запуск готовых бинарников с frontend. Показать отдельные шаги сборки, миграции, создания пользователя и запуска; не предполагать, что бинарник автоматически читает dotenv-файл. Обновить краткое описание текущего поведения приложения при реализации.

## Testing Decisions

- Граница тестирования согласована с пользователем: основная проверка — HTTP-запросы через существующий публичный Go-обработчик сервера, дополненные проверками конфигурации и отказа запуска при неверном каталоге. Отдельная обязательная браузерная инфраструктура с настоящим backend для этой задачи не требуется.
- Хороший тест проверяет наблюдаемое поведение: HTTP-статус, тело, заголовки, доступность файла, отказ доступа или результат подготовки сервера. Не проверять устройство маршрутизатора, число внутренних функций, использование конкретного файлового helper или порядок внутренних вызовов.
- Переиспользовать существующий подход с `httptest`, настоящими HTTP-запросами, временными каталогами и небольшими файлами-фикстурами. Для базовых проверок раздачи достаточно действующего in-memory-хранилища тестового приложения; не добавлять PostgreSQL, Docker или NAS в обязательные зависимости этих тестов.
- В качестве аналогов использовать существующие HTTP-контракты префикса и идентификатора запроса, cookie/CSRF и multipart-загрузки. Для настроек использовать существующие проверки публичного загрузчика конфигурации с временными каталогами и переменными окружения. При необходимости расширить существующую тестовую сборку приложения, не создавая второй независимый HTTP-стек для тестов.
- Проверить режим по умолчанию: API работает, корень и клиентские страницы возвращают прежний `404`, каталог сборки не требуется. Проверить явное пустое значение новой настройки.
- Проверить включённый режим для `/` и одного непустого `BOOK_HUB_BASE_PATH`: корень, прямые переходы на страницу библиотеки и страницу читалки, реальные ресурсы, query string, перенаправление корня подпути, недоступность посторонних префиксов и точность границ API-префикса.
- Проверить, что успешный API-запрос и его заголовки, cookie/CSRF, неизвестный API-адрес, неподдерживаемый метод API и запрос защищённой книги без авторизации сохраняют прежние контракты. Включение frontend не должно подменять эти ответы HTML.
- Проверить MIME-типы как минимум HTML, CSS, `.js`, `.mjs` и `.wasm`, а также побайтовую выдачу представительных ресурсов pdf.js и DjVu.js. Не воспроизводить в Go-тестах внутренние алгоритмы рендеринга читалок.
- Проверить `HEAD` без тела, представительный `Range` для статического файла, правила кэширования HTML, ресурса с хэшем, изменяемого ресурса и ошибки. Проверить `405` и `Allow` для неподдерживаемого метода статической ветки.
- Проверить, что отсутствующие `.js`, `.mjs`, `.wasm`, CSS и ресурсы без расширения внутри зарезервированных каталогов возвращают `404`, включая запрос с `Accept: text/html`, а не успешную SPA-подстановку.
- Проверить попытки выхода из корня, кодированные варианты пути, ссылку наружу, скрытый файл и отсутствие листинга каталогов. Во временном соседнем каталоге разместить файл-маркер и убедиться, что его содержимое никогда не выдаётся. Учесть доступность создания символических ссылок в ОС, не ослабляя основную проверку изоляции.
- Проверить ошибки подготовки HTTP-сервера при отсутствующем каталоге, обычном файле вместо каталога, отсутствующем `index.html` и недоступном HTML там, где права ОС позволяют воспроизвести отказ. Ошибка возникает до начала приёма запросов. Административный загрузчик настроек не должен зависеть от наличия сборки.
- При реализации выполнить backend-тесты и production-сборку frontend. Один раз проверить настоящий собранный frontend через Go-сервер: прямое открытие страницы, вход, загрузку и чтение книг, включая загрузку worker и WASM. Это проверка совместимости поставки, а не новый обязательный браузерный стенд. Существующие frontend-тесты сохраняются; дополнительные E2E запускать при изменениях их области и сообщить фактический объём проверок.

## Out of Scope

- Установка на конкретный NAS, перенос Entware, форматирование USB, настройка RAID, swap, сна HDD или автозапуска прошивки WD.
- Изменение штатного Apache либо установка nginx, Docker, chroot и других системных служб на устройство пользователя.
- Встраивание frontend в Go-бинарник через `go:embed`; в этой задаче сборка читается из указанного каталога.
- Автоматическая сборка frontend на сервере, dev server, HMR, наблюдение за исходниками и управление Node.js из backend.
- Гарантия безопасного обновления сборки на ходу. Обновление бинарника или каталога сборки выполняется администратором с перезапуском; атомарный updater и откат версий не разрабатываются.
- Новые форматы книг, изменение рендеринга читалок, модели доступа, API-контрактов, схемы БД или способов хранения исходных файлов книг.
- Изменение режима Docker по умолчанию, новая матрица ARM-сборок, пакеты приложений WD, универсальный установщик или система публикации релизов.
- Встроенное управление TLS-сертификатами, HTTP/3 и функции полноценного универсального веб-сервера.

## Further Notes

Практический мотив — установка на WD My Cloud EX2 Ultra и похожие устройства, но решение должно быть переносимым и не содержать логики, специфичной для WD, ARMv7, Entware или USB. Существующая сборка без CGO и поддержка SQLite позволяют рассматривать такой запуск без дополнительного сервера БД; новая возможность не ограничивается SQLite.

Производственная сборка frontend уже содержит необходимые ресурсы читалок. Их существующую синхронизацию при сборке сохраняют; Go-сервер раздаёт готовый результат и не воспроизводит эти сборочные шаги.

Для малошумного NAS бинарник, frontend, SQLite, локальные изображения, рабочую директорию и кэш файлов книг можно независимо разместить на USB, оставив исходные файлы книг на RAID. Новая раздача frontend сама по себе не гарантирует сон HDD: на него влияют расположение остальных данных, swap и штатные службы устройства.

Спецификация не меняет действующие ADR о СУБД, хранилище книг и кэше файлов книг. Настройка HTTP-раздачи не добавляет публичных HTTP API-операций, поэтому сама по себе не требует изменения OpenAPI или генерации frontend API-схемы.
