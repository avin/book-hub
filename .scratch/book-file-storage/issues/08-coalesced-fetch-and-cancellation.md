# 08: Объединение одновременных получений

**What to build:** одновременные запросы одной книги используют одно получение на экземпляр backend. Отмена клиента, ошибки и повторные запросы не обрывают соседние выдачи и не оставляют занятыми файлы или лимиты.

**Blocked by:** 07 — Постоянный локальный кэш с LRU.

**Status:** resolved

**Основание:** [спецификация](../spec.md), истории 26, 28, 30, 31, 34–37; ADR-0009.

- [x] Одновременные чтение и скачивание одного исходного файла вызывают одно получение на экземпляр backend, в том числе при запросах разных пользователей с подтверждённым доступом.
- [x] Объединение применяется к получению в кэш и к общему временному файлу при обходе кэша. Готовый временный файл остаётся доступным до завершения использующих его выдач.
- [x] Каждый запрос проходит свою проверку доступа до присоединения к получению; знание идентичности файла или наличие ожидающего владельца не открывает его чужому пользователю.
- [x] Уход одного ожидающего клиента не отменяет получение для остальных. При отсутствии ожидающих незавершённая операция отменяется, а временные файлы и резервы освобождаются.
- [x] После успешного общего получения каждый оставшийся запрос получает корректный ответ, включая свой диапазон или режим скачивания. Активная выдача не теряет файл из-за завершения другой выдачи.
- [x] Ошибка источника, целостности или локальной записи завершает ожидающие запросы корректной ошибкой. Следующий запрос может начать новое получение; зависшей общей операции не остаётся.
- [x] При одновременных отменах, ошибках и новых запросах соблюдаются отдельные бюджеты кэша и рабочей директории; учёт места не освобождается раньше фактического прекращения его использования.
- [x] Конкурентные HTTP-тесты используют управляемые события источника и наблюдаемое число получений вместо случайных задержек. Проверки с детектором гонок выполняются там, где применимы.

**Проверка результата:** одновременно запросить один отсутствующий файл несколькими клиентами, отменить часть запросов и завершить оставшиеся; затем отменить всех и повторить запрос, проверив число получений и освобождение места.

## Answer

Реализовано в `5b221ee` и `0e93387`. Общий для одного `files.Store` resolver объединяет получение по SHA-256 с независимым контекстом операции. Каждый HTTP-запрос после прежней проверки доступа получает отдельный файловый дескриптор; общий lease удерживает кэшированную копию или рабочий резерв до последней выдачи. Последний отменённый ожидающий клиент дожидается фактической очистки, а новый запрос не начинает получение поверх ещё занятого бюджета. Ошибка общего получения не блокирует повтор.

HTTP-проверки через управляемый источник подтверждают одно получение для разных владельцев, отмену одного и всех клиентов, закрытие источника посреди передачи, задержанную очистку и повтор, собственные диапазоны и позиции чтения, защиту рабочего файла до последнего ответа. Недоступность, неверный размер, SHA-256 и обрыв потока возвращают общую временную ошибку без частичных байтов; последующий запрос успешен. Проверки синхронизированы событиями источника и HTTP-контекста.

После объединения с integration `8fb37c5` прошли `go test ./...`, `go build ./cmd/...` и `go test -race ./internal/httpapi ./internal/storage/files ./internal/config`. Конкурентные сценарии и регрессия очистки отменённого запроса дополнительно прошли десять повторов с `-race`. Реальные протокольные сервисы, PostgreSQL и E2E в этой задаче повторно не запускались; их итоговая совместная проверка относится к 11/12. Публичный HTTP-контракт не изменён.
