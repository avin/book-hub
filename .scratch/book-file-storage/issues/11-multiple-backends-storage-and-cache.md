# 11: Совместная работа нескольких backend

**What to build:** два экземпляра backend на PostgreSQL используют общее хранилище оригиналов и независимые локальные кэши, сохраняя доступность книг и согласованность удаления при действиях через разные экземпляры.

**Blocked by:** 02 — Надёжное удаление оригиналов; 08 — Объединение одновременных получений.

**Status:** resolved

**Основание:** [спецификация](../spec.md), истории 15, 24, 26, 47–53; ADR-0007, ADR-0008, ADR-0009.

- [x] Два настоящих HTTP-экземпляра на общей PostgreSQL-базе работают с общим хранилищем оригиналов и разными директориями кэша и рабочих файлов.
- [x] Каждый экземпляр соблюдает собственные лимиты. Заполнение, вытеснение, перезапуск или неисправность одного кэша не повреждают другой.
- [x] Одновременное получение объединяется внутри экземпляра; распределённое объединение или общая директория кэша не требуются. Наличие готовой копии позволяет конкретному экземпляру обслужить запрос без оригинала.
- [x] Авторизация и принадлежность записи проверяются независимо от наличия копий в кэшах. Удалённая пользовательская запись не становится доступной через другой backend из-за сохранённой копии.
- [x] Загрузка одинакового содержимого и удаление последней ссылки через разные экземпляры не уничтожают используемый оригинал. Проверка защищает фактическое удаление, а не только предварительное чтение ссылок.
- [x] Сохраняемая очередь обрабатывается согласованно при нескольких экземплярах, сбоях и перезапусках; задача, созданная admin CLI, подчиняется тем же гарантиям.
- [x] Локальные изображения сохраняют прежние требования доступности для обслуживающих их экземпляров; тестовая установка предоставляет их согласованно, не подменяя это общим кэшем.
- [x] Конкурентные сценарии воспроизводятся управляемыми событиями на реальной PostgreSQL. SQLite сохраняет поддержку одного backend; обещание нескольких экземпляров на SQLite не добавляется.
- [x] Инструкции многопроцессной установки явно различают общее хранилище оригиналов и отдельные локальные кэши, пути и бюджеты.

**Проверка результата:** прогреть разные кэши двух HTTP-экземпляров, независимо заполнить один из них и выполнить конкурентные загрузку и удаление общего файла через разные экземпляры; после перезапуска проверить сохранность доступных книг и обработку очереди.

## Answer

Подтверждено в `6fcf9cc` через четыре сценария `TestMultipleBackends*` в
`backend/internal/httpapi/multiple_backends_test.go`. Каждый сценарий создаёт изолированную PostgreSQL-схему,
два HTTP-сервера с независимыми подключениями, кэшами и рабочими каталогами, общий источник оригиналов и
локальные изображения. Проверены вытеснение, разные бюджеты, перезапуск и неисправность одного кэша,
чтение из другого без оригинала, доступ к общей обложке и запрет выдачи удалённой или чужой записи.

Конкурентные HTTP-загрузки, физическое удаление и второй обработчик очереди синхронизируются барьерами
источника и фактическим состоянием `Lock` в `pg_stat_activity` по отдельным `application_name`, без проверки
SQL-текста и ожиданий наугад. Проверены сохранение общего оригинала, повторная загрузка после удаления и
задача удаления пользователя через ту же операцию storage, которую использует admin CLI: сбой, закрытие всех
подключений, перезапуск backend и успешный повтор другим экземпляром. Независимые получения и рабочие
резервы двух экземпляров дополняют HTTP-проверки объединения запросов внутри экземпляра из задачи 08.
Изменения production-кода не потребовались.

Прошли host-проверки с реальной PostgreSQL и `-race`, сборка `go build ./cmd/...`, затем после слияния
integration `23ca4e0` — Linux `go test -p 2 -race ./internal/httpapi -run TestMultipleBackends -count 2`
с реальной PostgreSQL. Команда и требования многопроцессного запуска описаны в `DEV.md` и `README.md`;
поведение отражено в `docs/APP.md`. Frontend/E2E не повторялись: HTTP-контракт и клиентский код не изменены.
