# 02: Надёжное удаление оригиналов

**What to build:** удаление книги сразу убирает её из библиотеки, а оригинал без владельцев надёжно удаляется через сохраняемую очередь. Временный сбой хранилища и конкурентная повторная загрузка не приводят к потере используемых файлов.

**Blocked by:** 01 — Разделить хранение файлов книг и изображений приложения.

**Status:** resolved

**Основание:** [спецификация](../spec.md), истории 46–51; ADR-0008.

- [x] Удаление пользовательской записи сразу убирает книгу и связанные с ней данные из библиотеки; сбой удаления оригинала не отменяет этот результат. Локальные обложки обрабатываются как прежде.
- [x] Общий оригинал сохраняется, пока существует хотя бы одна пользовательская ссылка. Задача удаления появляется при удалении последней ссылки и сохраняется надёжно вместе с изменением состояния библиотеки.
- [x] Очередь хранится в БД, переживает перезапуск и повторяет удаление после временных сбоев. Уже отсутствующий оригинал не оставляет бесконечно невыполнимую задачу.
- [x] Перед повтором проверяется отсутствие новых ссылок; эта проверка и удаление согласованы с конкурентной загрузкой того же содержимого. Одна предварительная проверка без защиты последующего удаления не считается выполнением требования.
- [x] Две конкурентные загрузки одинакового нового файла не приводят к удалению общего оригинала при конфликте или откате одной из них.
- [x] Удаление пользователя через admin CLI использует тот же жизненный цикл. При остановленном backend задача сохраняется для последующей обработки.
- [x] Необходимые миграции и операции поддерживаются на SQLite и PostgreSQL с сохранением штатного порядка миграций.
- [x] Проверки с реальными SQLite и PostgreSQL воспроизводят сбой удаления, перезапуск, повторную загрузку и конкурентный доступ через независимые подключения. Межпроцессная защита PostgreSQL не подменяется блокировкой внутри одного процесса.

**Проверка результата:** отключить удаление в управляемом источнике, удалить последнюю пользовательскую запись, перезапустить обработчик и восстановить источник; оригинал должен удалиться, а вновь используемый оригинал — сохраниться.

## Answer

Реализация: `3915dfa` — очередь `original_deletions` с миграциями PostgreSQL 000004 и SQLite 000002; удаление записи и постановка задачи выполняются одной транзакцией. HTTP и admin CLI удаляют локальные обложки, а оригинал обрабатывает фоновый worker backend. Сбой оставляет задачу для повтора после перезапуска.

`CreateBookWithOriginal` согласует фактическую публикацию оригинала и новую пользовательскую ссылку с worker: PostgreSQL использует транзакционную advisory-блокировку SHA-256, SQLite — `BEGIN IMMEDIATE`. Незавершённое подтверждение удаления учитывается при повторной загрузке: принятый файл публикуется заново перед восстановлением ссылки. Прямое удаление оригинала при откате загрузки исключено.

Проверки: `go test ./...` с настоящей PostgreSQL, `go build ./cmd/...`; Linux `go test -p 2 -race` для SQLite/PostgreSQL/memory storage, HTTP и admin CLI с тестами `TestOriginal`, `TestStoreContract`, `TestUploadDeleteLifecycle`, `TestDeleteUser` — успешно. Проверены независимые подключения, закрытие и повторное открытие БД, отмена конкурирующей загрузки во время физического удаления, повтор после удаления без подтверждения, общий оригинал и конкурентная дедупликация. PostgreSQL backup-тесты в Windows пропущены из-за отсутствия `pg_dump`/`psql`; они относятся к последующим задачам backup/restore. Frontend/E2E здесь не запускались: публичный HTTP-контракт и frontend не менялись.
