# 10: Backup/restore через удалённые хранилища

**What to build:** полный backup собирает оригиналы с FTP/FTPS/S3, а restore размещает их в выбранном локальном или удалённом хранилище. Администратор меняет тип хранения через прежние команды без отдельного инструмента переноса.

**Blocked by:** 04 — Полный цикл хранения в S3; 06 — Оба режима FTPS; 09 — Переносимый backup/restore для директорий.

**Status:** resolved

**Основание:** [спецификация](../spec.md), истории 54–61; ADR-0008, ADR-0010.

- [x] Backup собирает все нужные оригиналы из активного FTP/FTPS/S3-хранилища, БД и локальные изображения. Выключенный или частично заполненный кэш не ограничивает полноту; кэш в копию не включается.
- [x] Удалённое хранение не меняет привычный комплект и формат контейнеров копии. Недоступный или повреждённый необходимый оригинал не даёт успешно завершить полный backup.
- [x] Restore размещает оригиналы в текущем настроенном хранилище, изображения локально и пересчитывает ссылки БД. Исходный сервис после создания корректной копии не нужен.
- [x] До изменения данных проверяется пустота именно выделенной директории или префикса назначения. Чужие объекты вне этой области не затрагиваются; очистка всего FTP-сервера или бакета исключена.
- [x] Старые поддерживаемые архивы можно восстановить в новое удалённое хранилище при той же СУБД. Смена СУБД и отдельная команда миграции оригиналов не добавляются.
- [x] Сохраняются контроль размера и SHA-256, автоматический запуск после успешного backup и остановленное приложение после неудачного restore. Прерывание не выдаётся за успешное восстановление; повтор выполняется после ручной очистки выделенного назначения.
- [x] Интеграционная матрица включает локальное → удалённое, удалённое → локальное и удалённое → другой поддерживаемый тип, покрывает FTP, оба режима FTPS и S3 как источник и назначение. Используются локальные тестовые серверы и реальные адаптеры.
- [x] После каждого успешного восстановления проверяются файлы, обложки, метаданные и права через HTTP при недоступном исходном сервисе. Сценарий проверяется для SQLite и PostgreSQL в пределах одной СУБД.
- [x] Документация описывает backup → перенастройка → restore, пустое назначение, отдельную потребность в месте и сохранённый автоматический запуск после backup с принятым риском новых записей в промежутке.

**Проверка результата:** сделать полный backup удалённой библиотеки, отключить исходный сервис и восстановить копию в пустое хранилище другого типа; проверить доступность книг и изображений через приложение.

## Answer

Реализовано в `77cb52b`; интеграционная ветка с задачей 08 включена в `32520a9`.
Общий механизм backup/restore работает с реальными адаптерами директории, FTP, explicit FTPS,
implicit FTPS и S3 (Garage v2.5.0). Производственная правка дополняет предварительную проверку
размещения резервной копии каталогом кэша: копия не может писать в работающий кэш или содержать его.
Документация описывает смену типа хранения через backup → перенастройку → restore.

Проверки:

- Linux `go test -p 2 -race ./internal/backup -run TestRemoteBackupRestoresAcrossEveryStorageWithoutItsSource`:
  обе СУБД, по пять переходов directory → FTP → explicit FTPS → implicit FTPS → S3 → directory;
  исходные оригиналы, изображения и БД удаляются перед restore. Через HTTP проверяются байты книги,
  диапазон, обложка, миниатюра, метаданные и запрет чужому пользователю. Имена трёх частей копии сохранены,
  кэш и рабочие файлы в архиве отсутствуют.
- Linux targeted `-race` отрицательных проверок прошёл: warm cache не делает успешным backup при
  отсутствующем или повреждённом оригинале либо неверных учётных данных для каждого удалённого типа;
  непустое назначение сохраняет БД, оригинал и соседний namespace для обеих СУБД.
- Старые схемы SQLite 1 / PostgreSQL 3 и настоящий прежний tar с `./`, рабочими и служебными записями
  восстановлены во все четыре удалённых варианта; PostgreSQL без manifest поддержан. Служебные записи
  не загружаются как оригиналы. После прерывания restore сохранённый оригинал делает назначение непустым;
  повтор проходит только после ручного удаления собственного частичного результата.
- Post-merge host `go test -race ./internal/backup ./cmd/book-hub-backup ./internal/config` и
  `go build ./cmd/...` прошли. Ранее проверенные командные сценарии stop/start из задачи 09 сохранены.

Тестовые параметры: `BOOK_HUB_TEST_FTP_ADDR`, `BOOK_HUB_TEST_FTPS_EXPLICIT_ADDR`,
`BOOK_HUB_TEST_FTPS_IMPLICIT_ADDR`, `BOOK_HUB_TEST_FTPS_CA_FILE`, `BOOK_HUB_TEST_S3_ENDPOINT`,
для PostgreSQL дополнительно `BOOK_HUB_TEST_DATABASE_URL` и pg_dump/psql соответствующей версии.
Все удалённые тесты работают в уникальных каталогах/префиксах и удаляют только собственные объекты.
Отрицательный набор занял около 95 секунд: два FTPS-сценария отсутствующего файла достигают
ограниченного idle timeout около 30 секунд; успешные передачи и остальные проверки проходят быстро.
Frontend/E2E повторно не запускались: HTTP-контракт и frontend в этой задаче не менялись.
