# Поддержка SQLite и PostgreSQL

Состояние: согласована пользователем, реализована и проверена.

## Цель

При настройке сервера администратор может выбрать SQLite или PostgreSQL.

## Согласованные границы

Архитектурное решение: [SQLite и PostgreSQL как варианты базы данных](../../docs/adr/0007-sqlite-and-postgresql.md).

- Обе СУБД поддерживают все текущие функции приложения, включая нескольких пользователей, права доступа и сохранение прогресса чтения.
- Первый этап включает новую установку на SQLite и сохранение работы существующих установок PostgreSQL.
- Инструмент переноса данных PostgreSQL ↔ SQLite относится к отдельному этапу.
- Для SQLite поддерживается один экземпляр backend с базой на локальном диске сервера; несколько пользователей и устройств могут работать одновременно.
- Для нескольких экземпляров backend используется PostgreSQL.

## Конфигурация и эксплуатация

- Единственная настройка подключения — обязательная `BOOK_HUB_DATABASE_URL`; тип СУБД определяется по схеме URL. Отсутствие настройки считается ошибкой.
- Существующие PostgreSQL URL продолжают работать.
- Команды Make выбирают состав Compose по `BOOK_HUB_DATABASE_URL`; для прямого запуска Docker Compose документируются нужные файлы.
- Первый этап включает сервер, административную CLI, мигратор, Docker Compose, локальную разработку, резервное копирование и восстановление, CI и документацию.
- В SQLite-режиме PostgreSQL-контейнер не запускается и переменные `POSTGRES_*` не требуются; существующий запуск PostgreSQL сохраняется.
- Для обеих СУБД мигратор запускается отдельно перед сервером.
- SQL-миграции PostgreSQL и SQLite сопровождаются отдельно; существующая история PostgreSQL сохраняется.
- SQLite-файл создаёт только мигратор. Сервер и admin CLI при отсутствии базы или неподготовленной схеме завершаются с понятной ошибкой.
- Admin CLI поддерживает работу одновременно с сервером; миграции выполняются при остановленном сервере.
- SQLite использует абсолютный путь к локальному файлу. Формат настройки — `sqlite://` с последующим абсолютным путём; пример для Linux: `sqlite:///data/db/book-hub.sqlite`, для Windows: `sqlite:///C:/book-hub/data/book-hub.sqlite`.
- В Docker SQLite-файл размещается в отдельном постоянном volume; стандартный путь — `/data/db/book-hub.sqlite`. Книги и обложки сохраняют существующее файловое хранилище.
- Сервер и admin CLI проверяют версию миграций выбранной СУБД перед работой. Устаревшая, более новая или незавершённая схема отклоняется с объяснением причины.

## Резервное копирование и восстановление

- На время backup/restore приложение останавливается.
- Резервная копия включает согласованное состояние БД, файлов книг и обложек.
- Новые копии содержат указание СУБД.
- Старые PostgreSQL-копии продолжают восстанавливаться в PostgreSQL.
- Попытка восстановления в другую СУБД отклоняется до изменения данных.
- Во время миграций, backup и restore не выполняются другие операции записи через admin CLI или второй мигратор.

## Поиск и сортировка

- Поиск названия — буквальная подстрока без учёта регистра, включая кириллицу и латиницу.
- `%`, `_` и `\` в поисковом запросе считаются обычными символами; `е` и `ё` остаются разными буквами.
- PostgreSQL-поиск изменяется для соблюдения буквальной семантики спецсимволов.
- Точный алфавитный порядок отдельных символов, включая `ё`, цифры и пунктуацию, может различаться между СУБД; существующий алфавитный порядок PostgreSQL сохраняется.
- Сортировка `created_at_desc` исправляется: книги действительно выдаются от новых к старым.
- При равных основных ключах сортировки реализации используют одинаковое правило через ID книги; при неизменных данных порядок страниц должен быть устойчивым.
- Теги нормализуются существующей доменной функцией: удаляются пробелы по краям, регистр приводится к нижнему; существующие ограничения длины и количества сохраняются.
- После нормализации фильтр тегов использует точное совпадение и требует наличия всех выбранных тегов во всех реализациях хранилища.

## Устройство реализации

- SQLite получает самостоятельную реализацию существующего интерфейса `storage.Store`; PostgreSQL-реализация сохраняется.
- Реализации используют общий набор проверок поведения.
- Переход на ORM и переписывание PostgreSQL-реализации для добавления SQLite не требуются.
- Все бинарники продолжают собираться без CGO; SQLite-драйвер должен поддерживать этот способ сборки.
- SQLite-драйвер — `modernc.org/sqlite`; мигратор использует SQLite-адаптер существующего `golang-migrate`.
- Проверенный кандидат зависимости — `modernc.org/sqlite v1.61.0`, требующий Go 1.26.0 при проектном Go 1.26.4. Совместимость реальной сборки проверяется при реализации; обновляются необходимые транзитивные зависимости.
- При блокировке SQLite ожидание ограничено пятью секундами на операцию БД и учитывает отмену контекста запроса.
- Исчерпание ожидания блокировки возвращает HTTP `503` с кодом `service_unavailable` в существующем формате ошибки, включая операции авторизации. Временная недоступность не превращается в `401` и не сбрасывает авторизацию.
- Изменяющие HTTP-запросы целиком автоматически не повторяются. Неопределённый результат записи или COMMIT не является основанием для слепого повторения.
- Исправление существующих гонок при проверке квоты и обновлении метаданных относится к отдельной доработке backend.

## Технические решения

Детали согласованы вместе с итоговой спецификацией:

- Для SQLite включены WAL и проверка внешних ключей; настройки применяются ко всем физическим соединениям, включая admin CLI и мигратор. Используется `synchronous=FULL` для сохранения подтверждённых записей при сбое питания при корректной работе файловой системы и накопителя.
- Рабочая конфигурация принимает файловую SQLite-базу с абсолютным путём; относительные пути и in-memory-режим не являются поддерживаемой установкой сервера.
- Неподдерживаемая схема URL и некорректный путь отклоняются с понятной ошибкой; параметры URL не могут отключать обязательные настройки целостности.
- Для равных основных ключей сортировки используется `id DESC`; существующая сортировка relevance сохраняет ключи `last_opened_at DESC, created_at DESC, id DESC`.
- Новая резервная копия содержит `manifest.json` с версией формата, СУБД и версией схемы, данные БД (`database.sql` или `database.sqlite`) и `storage.tar.gz`. Старый набор `database.sql` + `storage.tar.gz` распознаётся как PostgreSQL-копия.
- SQLite-снимок должен учитывать WAL; копирование одного основного файла без учёта журнала не считается корректной резервной копией.
- До восстановления проверяются поддерживаемый формат, соответствие СУБД и наличие необходимых частей копии. При ошибке после начала восстановления приложение остаётся остановленным с диагностикой.

## Критерии приёмки

1. Новая установка SQLite запускается без PostgreSQL и `POSTGRES_*`; миграции и все административные команды работают. После перезапуска сохраняются пользователи, книги, обложки, теги, настройки, прогресс и сессии.
2. Существующая PostgreSQL-конфигурация продолжает работать; прежняя история миграций и старые резервные копии поддерживаются. До запуска требуется актуальная завершённая схема выбранной СУБД.
3. Общая storage contract suite проходит на memory, PostgreSQL и временном SQLite-файле. Покрыты изоляция пользователей, сессии, настройки, квоты, дедупликация, книги, обложки и прогресс в пределах существующего контракта.
4. Общие проверки покрывают буквальный поиск, кириллицу и латиницу, `%`, `_`, `\`, различие `е`/`ё`, нормализованные теги, сочетание фильтров и все объявленные сортировки. Равные основные ключи дают устойчивый порядок при неизменных данных; точное равенство алфавитного порядка разных СУБД не требуется.
5. Проверены server/admin при отсутствующем файле, неверном пути, старой, будущей и незавершённой схеме; запуск сервера или admin не создаёт пустой SQLite-файл.
6. Проверены одновременные запросы и работа admin рядом с сервером, снятие временной блокировки, ограничение ожидания и отмена контекста. При исчерпании ожидания API, включая авторизацию, возвращает 503 без ложного 401 и сброса сессии.
7. Для обеих СУБД backup/restore возвращает согласованную библиотеку с файлами. Проверены старый PostgreSQL-формат, SQLite-копия с учётом WAL и отказ от восстановления в другую СУБД до изменения данных.
8. CI обязательно выполняет контрактные проверки SQLite и PostgreSQL; SQLite не требует внешнего сервиса. Проверена сборка всех трёх бинарников с `CGO_ENABLED=0` и Docker-образа.
9. Проверены Compose-наборы для локальной сборки и GHCR, выбор стека через Make, миграции, готовность сервера и сохранность volume после пересоздания контейнеров.
10. Обновлены `api/openapi.yaml` для поиска и ошибок 503, frontend API-слой в необходимом объёме и сгенерированные типы через `make frontend-generate`; `docs/APP.md`, README и DEV описывают реализованное поведение.

## Порядок реализации

1. Разбор подключения, выбор адаптера и проверка версии схемы для server/admin/migrate.
2. SQLite-схема, миграции и реализация `storage.Store` с общими контрактными тестами.
3. Буквальный поиск, теги, сортировки и отображение временной недоступности в HTTP; синхронизация OpenAPI и frontend API-типов.
4. Постоянное хранение SQLite, Compose/Make, локальная разработка и административные команды.
5. Резервное копирование и восстановление для обеих СУБД с совместимостью старого PostgreSQL-формата.
6. CI, интеграционные проверки установки и восстановления, актуализация пользовательской документации.

## Проверки при передаче реализации

- `make backend-test` и обязательный запуск storage contract suite для PostgreSQL и SQLite.
- Сборка server, admin и migrate без CGO; сборка Docker-образа и релевантные Compose-проверки.
- Интеграционные проверки миграций, блокировок, авторизации и backup/restore.
- `make frontend-generate`, релевантные frontend unit-тесты, lint и typecheck/build после синхронизации API. E2E запускаются при изменении пользовательских сценариев; в отчёте указывается, были ли они выполнены.
